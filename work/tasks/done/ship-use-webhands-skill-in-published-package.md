## What to build

The published `webhands` tarball must CARRY the hand-authored `use-webhands` skill, and `webhands skills add` must install it FROM THE INSTALLED PACKAGE, with no clone of this repo present anywhere.

Today it carries no skill at all. Verified against the working tree at task-writing time:

- `packages/cli/package.json` `files` is `["dist", "src", "README.md", "LICENSE"]`; `npm pack --dry-run` in `packages/cli` emits 33 files, none matching `skill`. This matches the published 0.6.0 tarball.
- The skill is authored at the MONOREPO ROOT (`skills/use-webhands/SKILL.md`), i.e. outside the published package directory `packages/cli/`, so no `files` entry could have picked it up.
- `createCli()` (`packages/cli/src/cli.ts`) passes NO `sync` option to `Cli.create`. `skills add`/`skills list` come from `incur` for free, and `incur` only picks up hand-authored SKILL.md files through `sync.include` globs. So `webhands skills list` today lists the 26 auto-generated `webhands-<verb>` skills and NOT `use-webhands`. The command does not read the skill from a checkout: it does not read it at all.
- `README.md:79-80` already tells the user to "install the bundled skill: `npx webhands skills add` then look for `use-webhands`". That sentence is false today, which makes this a correctness fix, not a packaging nicety.

The consumer consequence is the reason this matters beyond tidiness: a skill sourced from a git CHECKOUT is mutable and unversioned, so it documents whatever branch that clone sits on rather than the installed binary's behaviour, and on NixOS it cannot be linked from the store path beside the binary the way `dorfl` and `memonaut` are. A skill inside the package is pinned to the release it documents and read-only by construction.

### Decisions this task RATIFIED

1. **WHERE it lands: `packages/cli/skills/use-webhands/SKILL.md`** — i.e. a top-level `skills/` in the PUBLISHED package, mirroring `offshoot-fanout` and `memonaut`, not `dorfl`'s `dist/skills/`. The skill is hand-authored source, and `dist/` in this repo is tsc output wiped and regenerated by `pnpm build`; putting authored prose there would claim it is generated. Two mechanisms force this over a prepack COPY from the monorepo root (the `README.md`/`LICENSE` pattern in `scripts/copy-publish-assets.mjs`): a copy is a gitignored generated artifact, which is the same dishonesty as `dist/`; and `incur`'s glob cwd resolves to `packages/cli/` in a checkout (see decision 2), so a root-only skill is invisible to `skills add` during development. MOVE the directory with `git mv`; do not leave a copy at the monorepo root.

2. **`skills add` must resolve from its own installed location, via an EXPLICIT `sync.cwd`.** Pass `Cli.create(binary, {..., sync: {include: ['skills/*'], cwd: <package root>}})`, where the package root is derived from the emitted module's own path (`import.meta.dirname` is `<pkg>/dist` at runtime because the tsc emit is flat, so the package root is its parent). Do NOT rely on `incur`'s default. Reading `incur@0.4.10` `src/SyncSkills.ts`: `sync()` defaults the glob cwd to `resolvePackageRoot()` (walks up from `realpath(argv[1])` to the first `package.json`), but `list()` defaults to `process.cwd()`. Relying on the defaults therefore gives an `add` that works and a `list` that silently omits the skill whenever the user is not standing in the package root. An explicit `cwd` makes both correct from any working directory. `incur` names the skill from the matched directory's basename (`use-webhands`), so it will not collide with the generated `webhands-<verb>` set.

3. **The skill's CONTENT needs no de-checkout-ing.** Grepped for checkout-shaped phrasing: the only two hits are `checkout` used in the retail sense ("let the HUMAN complete checkout") and a reference to `docs/adr/0002`/`0016`. The skill already addresses a reader who has the CLI installed and invokes it as `npx webhands <verb>`. Re-verified at build time; the file shipped BYTE-IDENTICAL to the authored source (diffed against the copy installed from the packed tarball).

4. **`files` must gain `"skills"`.** It is the actual gate on tarball contents and is the single-line cause of the omission.

5. **Generated skills collapse to ONE (`sync.depth: 0`), added during the build at the operator's request.** `incur`'s default depth of `1` emits one generated skill PER VERB — 26 of them — which buries the hand-authored skill in an agent's skill list under near-duplicates of a reference `use-webhands` already carries in full (it states outright that the reader need not run `--help`/`--llms-full`). `depth: 0` renders a single `webhands` command reference instead, so `skills add` installs exactly two skills. **Zero generated skills is NOT reachable in `incur@0.4.10`**: `SyncSkills.sync` renders the command map unconditionally and installs whatever it rendered, so one is the floor. Recorded because "only the one skill" was asked for and could not be fully honoured.

6. **`incur` was NOT upgraded.** `0.5.1` is available and may have fixed the `sync`/`list` cwd asymmetry that decision 2 works around. Upgrading the CLI framework is a larger, riskier change than this task and belongs in its own item; the explicit `cwd` is correct either way.

## Decisions

The six decisions above are the durable record. The three worth flagging to a reviewer, because they were choices rather than transcription:

- **`sync.depth: 0`** (decision 5) changes user-visible behaviour beyond the packaging fix: `skills add` used to install 26 skills and now installs 2. This was asked for explicitly; it is called out here because a reader of the diff would otherwise see only "one line added to a config object".
- **The package root is computed from the module's own URL** (`dirname(fileURLToPath(import.meta.url))` + `..`), documented at the resolution site in `packages/cli/src/skills.ts`. It works in `src/` and `dist/` alike ONLY because the tsc emit is flat; a nested emit layout would break it, which is why the packaging test asserts the resolution rather than trusting it.
- **The end-to-end install check is a release-time step, not a test.** Automating it needs a real pack plus a registry install, and `skills add` writes into the user's real agents-skills directory. The unit tests guard the three things that silently regress (path, `files`, depth); the full path was exercised by hand this time and is written up above.

## Prompt

> Ship the hand-authored `use-webhands` skill inside the published `webhands` npm package, so a consumer can install the package and run `webhands skills add` to get the skill, with no git clone anywhere on the machine.
>
> FIRST, check this task against current reality (it is a launch snapshot and may have DRIFTED). Specifically re-verify, and route to needs-attention rather than building on a stale premise if any of these no longer hold: `packages/cli/package.json` `files` omits skills; the skill lives at the MONOREPO ROOT `skills/use-webhands/SKILL.md`; `createCli()` in `packages/cli/src/cli.ts` passes no `sync` option to `Cli.create`; and the installed `incur` still defaults `SyncSkills.sync`'s glob cwd to `resolvePackageRoot()` while `SyncSkills.list` defaults to `process.cwd()` (read `node_modules/incur/src/SyncSkills.ts`; the version pinned at task-writing time was 0.4.10). That asymmetry is the reason this task insists on an explicit `sync.cwd`; if a newer `incur` fixed it, say so and simplify rather than carrying a workaround for a bug that is gone.
>
> Domain vocabulary (`CONTEXT.md`): `incur` is the CLI framework that gives this binary MCP, `--llms`, and agent skills for free; a `verb` is one agent-facing command. The 26 `webhands-<verb>` skills are GENERATED from the command map by `incur`; `use-webhands` is the hand-authored workflow + judgment layer and is a different kind of artifact. Both end up installed by the same `skills add`.
>
> Where to look, by concept rather than brittle path: the CLI builder that calls `Cli.create` in the `cli` package; that package's `package.json` `files`; the monorepo's publish-assets script (read it to understand the existing README/LICENSE copy pattern, and then deliberately do NOT use it here — see the Decisions section of this task); the existing vitest that asserts against the skill's sensitive-info rung, which hardcodes the skill's current path and must be repointed.
>
> The four decisions to implement are recorded in this task's "Decisions this task RATIFIES" section: authored location under the published package's own top-level `skills/`; an explicit `sync.cwd` derived from the emitted module's own directory so BOTH `add` and `list` resolve from the installed package; no content rewrite needed (re-verify); and `files` gains `skills`. Treat them as decided, but if building shows one of them wrong, change it and RECORD the change rather than silently diverging.
>
> RECORD non-obvious in-scope decisions durably and link them from the done record. The likely candidates here: how the package root is computed at runtime (and why not `process.cwd()` or `resolvePackageRoot()`), and whether the end-to-end "install the tarball and sync" check lives in CI or stays a manual release step. Neither obviously meets the ADR gate (hard to reverse + surprising without context + a real trade-off), so a module JSDoc at the resolution site plus a `## Decisions` block in the done record is likely the right home; use `docs/adr/` only if the choice turns out to be genuinely hard to reverse. An un-recorded in-scope decision is a review finding.
>
> Be careful with the global write: `skills add` installs into the user's real agents-skills directory. Do not let the test suite write there. Redirect `HOME` for any child process that performs a real sync and assert the real directory is untouched, or keep the tests to configuration and path-resolution assertions and leave the full install as a documented manual/CI check.
>
> Done means: the packed tarball contains the skill, a scratch install of that tarball can sync it with no clone present, the existing skill test passes against the moved file, a changeset exists with a defensible minor bump, and `pnpm format:check && pnpm build && pnpm test` is green.
