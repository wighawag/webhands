# Attach to the user's own Chrome rather than hardening a launch: what actually got past Akamai

In ONE measured session against a serious commercial bot manager (Akamai, on an authenticated Japanese rail booking site), a Playwright-LAUNCHED browser was blocked in **every** configuration tried: default launch, `--stealth` (with Patchright genuinely installed and resolved), `--stealth --use-system-browser chrome`, and a brand-new profile. A Chrome the HUMAN started (`google-chrome --remote-debugging-port=9222 --user-data-dir=...`) and webhands merely ATTACHED to drove a nine-screen authenticated flow, including login, search, seat selection and a payment page, with no blocking at all. So we make "drive the user's own real Chrome" a first-class, documented mode (`serve --real-chrome`: spawn the system Chrome with a debugging port on the dedicated profile dir, then attach over CDP), and we correct the README, which presented stealth plus a headed window as the realistic anti-bot recipe. That guidance was wrong. It lived in the README's stealth section and was never recorded as an ADR, so there is no prior decision to supersede; ADR-0002's core principle (a real browser, profile and IP, never spoofing) is untouched, because this is that principle taken further rather than a departure from it.

Scope of the evidence, stated plainly: one site, one vendor, one date, no committed artifact. It is enough to change which mode we recommend FIRST, and not enough to claim this mode defeats bot management in general.

## Why it works, honestly

Not because it hides automation. Chrome sets `navigator.webdriver === true` whenever `--remote-debugging-port` is enabled, verified in a plainly-spawned Chrome by a page's own boot script BEFORE any client attached. So the working recipe is just as "detectable" on that signal as the blocked one, and a site reading `navigator.webdriver` sees automation either way. What differs is everything else: no Playwright launch-hardening args, no emulated viewport, a real warm profile with history and prefs, a real window, and the human's own IP and behaviour. The practical lesson is that bot managers weigh the whole picture, so the productive move is to BE a real browser rather than to patch one tell at a time.

## Consequences

- The symptom to teach is deceptive: the static, edge-cached top page renders fine (so it looks like it works) while every dynamic endpoint returns a bare "Access Denied". Documentation and agents must check a DYNAMIC endpoint before concluding anything.
- `--real-chrome` owns a lifetime the attach transport deliberately does not: webhands spawned the browser, so closing the session terminates it, unless `--keep-browser` is passed. The rule is OWNERSHIP, not the flag: a browser merely reused is left running either way.
- The profile dir is the same dedicated `profiles/<name>` every other mode uses, and it is created by this mode's first run (which IS its setup, since the window is visible and the human logs in by hand). A dir is written by the browser BUILD that opened it, so do not point `--real-chrome` at a profile `setup-profile` created with bundled Chromium; give it its own `--profile`. (Since the addendum below, `setup-profile --real-chrome` writes the profile with that same Chrome, so it is the right way to prepare a `--real-chrome` profile.)
- The Playwright LAUNCH-hardening flags (`--stealth`, `--use-system-browser`, `--no-viewport`) do not apply in this mode: there is no Playwright launch to harden. `serve` warns rather than ignoring them silently, and warns too when an explicit `--endpoint` makes the whole bring-up policy moot.
- `--proxy` DOES apply, mapped onto Chromium's own `--proxy-server` plus the `--host-resolver-rules` no-leak catch-all, and it is the only lever on the exit IP in this mode. Chrome implements no SOCKSv5 authentication and ignores credentials embedded in proxy settings, so a credentialled URL is REFUSED (`ProxyAuthUnsupportedError`) rather than silently sent unauthenticated; loopback stays unproxied per Chromium's implicit bypass list. See `work/notes/findings/chrome-cli-proxy-limits-no-socks-auth-and-loopback-bypass.md`.
- Any open REUSES a browser already live on that profile dir (Chrome cannot open one user-data dir twice, and a crashed controller or a previous `--keep-browser` run can leave one up), attaching with detach-only semantics because that browser is not ours to kill. Reuse is therefore NOT gated on `--keep-browser`; what the flag decides is whether the browser webhands STARTED survives `stop`. A reused browser cannot acquire spawn-time options, so asking for `--proxy` while one is running is a refusal (`RealChromeReuseConflictError`), not a silent downgrade.
- CDP exposure on a LAUNCHED browser became opt-in (`--expose-cdp`) as part of the same correction: it was hard-coded on, which added a remote-debugging port to every session, including under `--stealth`.
- The seam is unchanged (ADR-0003): this is a transport handling `mode: 'launch'`, with "which browser and how" staying transport-construction policy. The spawn half (`spawnRealChrome`) imports no Playwright and hands back a plain loopback URL string; the driving half is the existing attach transport, unmodified.
- Scope (ADR-0002) is unchanged: this starts a normal browser the user could have started themselves and lets them log in with their own hands. No captcha solver, no fingerprint spoofing, no provider key.

## Addendum (2026-10-25): it beats Akamai, not Cloudflare Turnstile

Measured on one host against Luma's sign-in (Cloudflare Turnstile) and Google sign-in: `serve --real-chrome` was refused, while the same Chrome binary started with NO debugging port passed Turnstile with one click (finding `cloudflare-turnstile-refuses-any-browser-with-a-debugging-port`). Turnstile refuses on the `navigator.webdriver` bit that this ADR already documented as present in this mode; Akamai weighed the whole picture and let it through. So the decision stands, scoped: attaching to the user's own Chrome is the first answer to Akamai-class bot managers, and it is NOT an answer to a check that reads `webdriver`.

What changed because of it: `setup-profile` no longer opens its window through Playwright. It spawns the browser as a plain process (no `--remote-debugging-*`, no `--enable-automation`, no Playwright default args), with the same build that will later drive the profile (`setup-profile --real-chrome` for this mode). The login a human does there carries over to `serve --real-chrome` on the same profile. What it cannot fix: a site that re-challenges on an ACTION sees `webdriver` again under `serve`, and a human has to do that step in a portless browser. Removing the flag for automation itself would need a driver with no CDP at all (ADR-0003's extension transport), captured as an idea, not decided.

## Addendum 2 (2026-10-25, later): `--hide-webdriver`, opt-in

The addendum above was right about the signal and too pessimistic about the cost of removing it. Chrome's `--disable-blink-features=AutomationControlled` keeps `navigator.webdriver` false with the debugging port still open. With it, `serve --real-chrome` passed Luma's Turnstile at sign-in (twice; the control without it was refused) and on an action-level re-check (Request to Join), all with CDP clicks (finding `turnstile-passes-cdp-with-automation-controlled-disabled`). For that check the bit WAS the whole signal, so the Playwright transports, hands and `script` included, can be used there.

We expose it as an explicit, OPT-IN flag, `serve --real-chrome --hide-webdriver`, rather than an env var or a default. A flag makes the choice visible in the command an agent or a human runs. It stays off by default for three reasons. Chrome shows an "unsupported command-line flag" infobar, which pages cannot read but which takes about 56px of viewport. It hides one signal and nothing else. And "real Chrome, as the user would run it" stays the honest default of this mode. When a browser that was started WITHOUT the flag is reused, the effect is checked: if it reads `navigator.webdriver` as true the reuse is refused (`real-chrome-reuse-conflict`) rather than silently showing the bit. Outside `--real-chrome` the flag warns that it does nothing.

Relation to ADR-0018: the extension transport stays the answer for a check that detects CDP itself, which this flag cannot hide. The order to try is `--real-chrome`, then `--real-chrome --hide-webdriver`, then `--transport extension`.
