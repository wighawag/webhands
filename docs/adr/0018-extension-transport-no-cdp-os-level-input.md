# The extension transport: no CDP anywhere, a WebSocket bridge to the service worker, Playwright's own selector engine in the content script, and OS-level input

We build the transport ADR-0001/0002/0003 deferred: `serve --transport extension` drives a plain Chrome-family browser (no `--remote-debugging-*`, no `--enable-automation`, so `navigator.webdriver === false`) through a small MV3 extension, and performs every pointer and keyboard action as trusted OS-level input from the controller. We chose this because one measured session (finding `cloudflare-turnstile-refuses-any-browser-with-a-debugging-port`) showed Cloudflare Turnstile refusing every CDP-based mode, including on an action after a human login, while the same Chrome with no debugging port, driven by xdotool, passed with one click. Removing CDP and using trusted input was the difference, so the transport removes exactly those two things and keeps everything else (the verb seam, the controller-owned loop, the dedicated profile) as it is. The Playwright transport stays the default.

## The decisions

**Bridge: the controller is a loopback WebSocket SERVER; the extension's service worker is the CLIENT.** The service worker is where every API we need lives (`tabs`, `cookies`, `windows`, `captureVisibleTab`, messaging to content scripts), so it is the natural endpoint. Chrome 116+ keeps a service worker alive while it exchanges WebSocket messages, so the controller sends an application-level `ping` every 20s. ADR-0001 still holds: the extension is a STATELESS executor. Every command names its tab and frame, so a worker that is killed anyway loses nothing but the command in flight. Its top-level code reconnects on every start. Something has to START it, though: an MV3 worker only runs when an event reaches it, a top-level `about:blank` gets no content script, and alarms are not guaranteed to survive a browser restart. So the browser opens an inert page served by the bridge itself, and every top-level content-script load sends the worker a wake message; a `chrome.alarms` tick (30s) covers the rest. A command in flight when the socket drops REJECTS with a disconnected error. It is never replayed, because a click is not idempotent. Discovery: before the browser starts, `serve` writes `config.json` (port, per-session token) into the extension directory `<home>/extension/` (0700 dir, 0600 file). The worker reads it with `fetch(chrome.runtime.getURL('config.json'))` on each connect. That read is live from disk for an unpacked extension, so the same stable directory works across sessions. The SCRIPTS are not: Chrome kept running a stale cached service worker after the files changed (measured on 156), so the worker, content and injected scripts are written under content-hashed names, with the manifest version derived from the same hash. Authentication is MUTUAL and the token never crosses the wire: the handshake must carry `Origin: chrome-extension://<pinned id>` (the id is fixed by a public `key` in the manifest); the worker sends a nonce, the server answers with an HMAC of it under the token plus its own nonce, and the worker answers that (compared in constant time). The worker obeys nothing until the server has proved it holds the token, so whatever later binds a stale port learns nothing and commands nothing. `serve` also writes an inert `config.json` on teardown, so a later plain start of the profile does not dial at all. The listener binds 127.0.0.1 only.

**Addressing: the SAME engine Playwright uses, split the same way Playwright splits it.** The locator EXPRESSION (ADR-0004) is evaluated in Node exactly as the Playwright transport evaluates it (`new Function('page','p', ...)`), but against a recording `page` that builds Playwright's internal selector string with the selector-construction rules of Playwright's client `Locator`/`FrameLocator` (ported from `isomorphic/locatorUtils`). The content script runs Playwright's own `InjectedScript`, extracted at runtime from the pinned `playwright-core` (the same source Playwright injects into its own isolated "utility world", so the environment matches). Frame hops (`internal:control=enter-frame`) are split in Node, as Playwright's server does. Each prefix must resolve to exactly one `<iframe>`. The content script posts a nonce into `iframe.contentWindow`; the child frame's content script consumes it at `document_start` in the capture phase with `stopImmediatePropagation` (so page listeners never see it) and reports to the worker, which learns the `frameId` from `sender.frameId`. `chrome.runtime.getFrameId` would be cleaner, but Chrome does not have it (it is Firefox-only, measured). Content scripts run in every frame, cross-origin included (`all_frames`, `match_origin_as_fallback`, `<all_urls>`). This corrects ADR-0010's assumption that a content-script transport cannot reach nested cross-origin frames: it cannot SCRIPT across them from the parent, but it has its own script INSIDE each one, and OS input does not care about origins. Parity: the whole selector grammar (`getBy*`, CSS/XPath/text engines, chains, `filter`/`has`/`hasText`/`visible`, `nth`/`first`/`last`, `and`/`or`, `frameLocator`/`contentFrame`/`owner`) plus snapshot `aria-ref=eN` refs, because the snapshot and the resolution share one `InjectedScript` per frame. A locator method that is not selector-building (`evaluate`, `page()`, ...) fails at COMPILE time with a typed `unsupported-by-transport` error naming the method. It never degrades silently.

**Input: OS-level, from the controller; never `chrome.debugger`.** Content-script events are `isTrusted: false`, and that is exactly what an anti-bot check reads. `chrome.debugger` is rejected: it IS the DevTools protocol attached to the tab, behind an infobar ("... started debugging this browser"), and it brings back the signals this transport exists to remove. So `click`, `type`, `press` and `mouse` (and later `hover`, `drag`) are XTest input via `xdotool` on X11. The content script reports the element's box in viewport CSS pixels, composed through the iframe chain (iframe rect plus `clientLeft/Top` plus padding). The controller converts it to screen pixels with the window's viewport origin and device scale. The geometry is then VERIFIED: after the pointer moves, the content script reports the trusted `mousemove`'s `clientX/Y`, and a miss is corrected from that event's exact `screenX - clientX` before pressing. A miss that persists after correction fails loud. Actionability mirrors Playwright's checks: attached, visible, enabled, stable over two animation frames, scrolled into view, and hit-tested at the click point. Verbs that need no input event stay in-page: `goto`, `wait`, `snapshot`, `query` and its shorthands, `cookies`, and `screenshot`. `wait` for a locator is a pure read (matches exactly one element, and it is visible), like Playwright's strict `waitFor()`: it neither scrolls nor demands actionability. `--dom` keeps its existing meaning: a dispatched, untrusted event, opt-in. Wayland (uinput/`ydotool`), macOS (Quartz `CGEvent`, which needs the Accessibility permission) and Windows (`SendInput`) sit behind the same `InputBackend` interface and are designed, not built. Without a backend the transport fails `os-input-unavailable` instead of falling back to untrusted events.

**Display: its own Xvfb by default.** OS input drives a whole display. On the user's desktop it would move their real pointer, and it needs the browser window focused. So the transport starts its own `Xvfb` (`-displayfd`, `-dpi 96`, `-nolisten tcp`), puts one browser window at (0,0) and kills the display on close. `--headed` uses the current `DISPLAY` and warns that the pointer will move. Chrome's `--headless` is rejected: it is itself a fingerprint, and it has no X display to send input to.

**Launch: a plain process, like `setup-profile`.** The flags are `--user-data-dir`, `--no-first-run`, `--no-default-browser-check`, `--load-extension=<home>/extension`, `--window-position=0,0` and `--window-size`, and nothing else except the operator's `WEBHANDS_CHROME_ARGS` (a container may need `--no-sandbox`), which is refused if it carries a `--remote-debugging-*`, `--enable-automation` or `--headless` flag. Chromium and Chrome for Testing (Playwright's pinned build, the default browser here as for every other mode) honour `--load-extension`. Branded Google Chrome 137+ silently IGNORES it (measured on 156). `Extensions.loadUnpacked` over a debugging pipe installs an extension that is dropped at the next plain start (measured), and a per-profile `External Extensions` JSON is not honoured (measured). What does persist is a HUMAN "Load unpacked" of the stable directory in `chrome://extensions` (Developer mode), once per profile. So `serve --transport extension --real-chrome` on branded Chrome requires that one-time step, `setup-profile --transport extension` writes the directory and prints it, and a worker that never says hello is the typed `extension-not-connected` error naming the step. The enterprise-policy route (`ExtensionInstallForcelist`, root plus a "managed" banner) is documented as an operator option and not automated.

**Permissions: the minimum for the verbs.** `cookies`, `alarms`, host `<all_urls>` (content scripts everywhere, any domain's cookies, `captureVisibleTab`). The manifest declares NO `web_accessible_resources` (a page cannot probe for the extension), no `externally_connectable`, no `debugger`, no `nativeMessaging`, no `scripting`, and not even `tabs` (the host permission already exposes tab URLs).

**Hands: none.** A hand receives a live Playwright `Page` (ADR-0006/0007), and this transport has none. CONTEXT.md already says a transport that cannot hand over live page access offers no hands. `script`, which hands a Playwright page, is `unsupported-by-transport` for the same reason. A reduced hand context is not defined until a hand needs one.

## Considered Options

- **Native messaging (rejected):** the BROWSER spawns the host process, which inverts ADR-0001's ownership (the host would just relay to `serve`), needs a host manifest per browser and OS, and its port is still bound to the service worker's lifetime.
- **WebSocket held by a content script (rejected):** it lives per tab, dies on every navigation, and runs in the page's origin. **Held by an offscreen document (rejected):** it survives longer, but it only has `chrome.runtime`, so every command would still hop through the worker. It adds a hop and does not remove the dependency.
- **`chrome.debugger` for input (rejected):** see above. It is CDP with an infobar.
- **A bespoke locator engine in the content script (rejected):** ADR-0004's floor is Playwright-equivalent semantics, and Playwright's own engine is the only honest way to meet it.

## Consequences

- ADR-0003 is honoured as written: the seam is unchanged and this is one more `Transport` behind it. ADR-0010's coordinate contract is unchanged too (`mouse` takes VIEWPORT CSS pixels): the transport, not the caller, converts to screen pixels. ADR-0010's line "webhands never injects OS input" is now scoped to the Playwright transports.
- The slice ships `goto`, `wait`, `snapshot`, `click`, `type`, `press`, `mouse`, `cookies` (export/import/clear), `query`/`count`/`exists`/`is-visible`/`get-attribute` (no `--with-refs`), and a viewport `screenshot`. Every other verb (`eval`, `script`, `hover`, `select`, `scroll`, `drag`, element/full screenshots) is `unsupported-by-transport`, naming the verb and the Playwright transport as the alternative. Snapshots do not inline child frames.
- `click` does NOT fall back to a dispatched click when the element never becomes actionable (the Playwright transports do, and report `via: dispatch`, ADR-0015). It waits (10s default) and fails, because a silent untrusted click is what this transport exists to avoid. `--dom` still asks for one explicitly.
- `--expose-cdp` with this transport is a refusal: there is no CDP to expose, and pretending otherwise would defeat the mode.
- Trust (ADR-0005/0012) is unchanged in kind: the extension is a code-execution surface on every logged-in page of the profile it is installed in, like `eval`. It is only ever installed into a dedicated webhands profile, it obeys only a loopback peer holding the per-session token, and it ignores everything else.
- Measured later the same day (ADR-0014 addendum 2): on Luma the CDP path also passes once `navigator.webdriver` is hidden (`serve --real-chrome --hide-webdriver`), and hands work there. This transport is the next rung, for checks that detect CDP itself, not the only route.
- Scope (ADR-0002) is unchanged: this is the user's own browser, profile and IP, no fingerprint spoofing, no captcha solving. A human still does the login. What changes is that the AUTOMATION no longer announces itself through a debugging port.
